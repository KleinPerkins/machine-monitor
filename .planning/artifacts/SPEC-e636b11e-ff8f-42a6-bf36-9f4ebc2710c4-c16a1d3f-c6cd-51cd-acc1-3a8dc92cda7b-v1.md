# Private Mac application delivery: Machine Monitor first consumer

## Authority and ecosystem fit

Implement all eleven REL-001–REL-011 requirements in the approved Private delivery and automatic updates PRD, version 1. Canonical engine trace aliases REQ-MONITOR-REL-001 through REQ-MONITOR-REL-011 correspond one-to-one to the REL identifiers. The original ten aliases are unchanged; REQ-MONITOR-REL-011 traces the added Free-only requirement. Existing owner platforms are Vercel and Cloudflare; Sterling already integrates Sparkle 2.10.1 and ShadowSync requires it. Use GitHub source/release governance, stock pinned Sparkle for native replacement, and Cloudflare for private artifact/access delivery. Vercel remains available for richer web experiences; it is not a prerequisite for these downloads.

Keep implementation in machine-monitor initially, with a versioned app/channel/release contract and per-app namespaces so later extraction/reuse is possible. Do not create a speculative fleet platform or migrate other products. Separate update signing keys, recipient grants, release channels and publishing authority for each app. The PR controller's host and execution boundary remain unrelated. No billable plan, account upgrade, checkout, trial conversion or material cost commitment is authorized. The selected account must remain positively qualified as Workers Free.

## Components and data flow

1. Owner release tooling builds only qualified merged source, pins build dependencies and official Sparkle 2.10.1 (archive SHA256 1a856d2a9edb8e628de88121d7be04cf0e2167f8641650b78fca00b14244cf27), embeds the public update key and approved HTTPS origin, signs nested code inside-out with hardened runtime/timestamps, obtains notarization acceptance, validates a stapled ticket and Gatekeeper, and emits an immutable release manifest with artifact hashes and provenance. Preserve Sparkle's license/notices. Ad-hoc/source and fixture builds do not contact production updates.
2. A Cloudflare Worker authorizes every protected request using an app-scoped recipient credential. D1 stores token hashes, opaque grant IDs, app/channel entitlements, expiry and revocation; Workers Static Assets stores immutable binary parts behind unconditional Worker authorization; no external part route is public. No public GitHub binary assets. Worker responses for protected metadata/downloads are private/no-store with no public cache path, cross-origin access or redirect. Revocation affects subsequent requests, not already downloaded bytes or a response already in flight. D1 checks must use current primary state; service/query failure denies access.
3. Native UpdateCoordinator reads only its own Keychain credential, automatically checks on launch after dashboard startup and every six hours while the app runs, and provides Check for Updates. Its own ephemeral URLSession has cookies/cache disabled, default TLS validation and a delegate that rejects every redirect. It sends the recipient credential only to the exact compiled HTTPS origin (scheme/host/port), never to feed-provided arbitrary URLs. Requests and responses have size/time limits and stream archives to an owned private temporary file. No metrics or process data leave the Mac.
4. Before involving Sparkle, verify archive length, SHA256 and Ed25519 publisher signature against the app's embedded public key. A separate import-safe Python module, included in the signed frozen service and selected by an explicit preflight-only CLI mode before Engine initialization, inspects ZIP metadata and safely extracts a duplicate into an owner-only temporary directory. It refuses traversal, absolute/drive paths, duplicate or case/Unicode-colliding entries, special files, symlink escapes/chains outside the app, writes through symlink parents, excessive entries/expanded size/ratios counted during actual streaming, local-header/central-directory disagreement, malformed filename encodings/metadata and unexpected top-level payloads. Native Security APIs then validate the extracted application's strict code signature, expected Developer ID team, bundle ID, increasing build, arm64 payload and macOS26 compatibility. This preflight never starts the collector or app. Only a fully verified archive can become ready.
5. Stock Sparkle does not receive recipient credentials or contact the external private service. When installation is allowed, a short-lived NWListener bound strictly to 127.0.0.1 on an allocated port exposes one unpredictable per-session path for a generated appcast and the already verified archive. It permits bounded GET/HEAD requests with exact Host/path, no CORS, traversal, redirects, extra assets or collector API; limits headers, connections and deadlines. The feed carries the real EdDSA signature. Serve the already-verified archive through a retained read-only file descriptor, with length/hash checked before admitting it; refuse inode/path substitution and keep it alive until Sparkle has consumed the bytes. The random local path is an ephemeral bearer capability and is neither persisted nor logged. Enable SUVerifyUpdateBeforeExtraction, retain normal archive EdDSA verification, and omit release notes, deltas, alternative downloads and arbitrary links. The locally generated feed itself is not represented as a publisher-signed external feed. Sparkle re-verifies its normal update signatures and performs replacement/relaunch. This preserves stock framework packaging instead of maintaining a Sparkle fork or custom replacement engine.
6. The coordinator owns scheduling with an explicit state machine: idle -> checking -> downloading -> preflighting -> ready -> admitting -> installer-pending -> replacement-observed -> accepted, plus cancelled/error/recovery-required. Never construct/start Sparkle on ordinary startup before installation admission. Set SUEnableAutomaticChecks=NO, SUAllowsAutomaticUpdates=YES and SUAutomaticallyUpdate=YES in the controlled updater configuration. Assert effective allowsAutomaticUpdates/automatic-download settings before activation; setting downloads with automatic checks disabled otherwise does not take effect in Sparkle 2.10.1. On the main thread use one retained SPUUpdater only for the admitted release, with the dynamic feed delegate already bound, then startUpdater and checkForUpdatesInBackground. The coordinator preferences remain the admission authority, independent of Sparkle settings. At admission, set a dynamic feed delegate to the live loopback handoff, use background checking with automatic download/install enabled, and retain the willInstallUpdateOnQuit immediate handler. Sparkle's cycle-finished/sessionInProgress flags are not installer-completion evidence. Journal the transaction ID, exact admitted release/hash, target identity/path, current boot identity, backup manifest, credential generation and phase before Sparkle activation. Every main-app and Recovery startup acquires the same operation lock before journal reconciliation or any collector/update activation. For an expected successful install-on-quit with no relaunch marker, verify the exact expected installed build/signature, recorded replacement conditions and dormant native/service readiness, then resolve the journal; an explicit user launch may then begin its normal first scan. A valid automatic-relaunch marker keeps that launch dormant. Pending/unknown or wrong-build state starts in recovery-required without a collector scan or new Sparkle activation. If another restoration owns the startup lock, quit cleanly and require reopening; do not continue a process across on-disk restoration. Qualify cached/deferred installer resume and reject unexpected release identity before continuing.
7. Installation admission is a collector-side lease acquired atomically under the same lock as Engine.start, only when there is no active scan or already admitted operation. All dashboard/native/queued HTTP start routes take that lock and reject while leased. Unavailable state defers installation. The coordinator downloads/stages during scans but obtains the lease before any Sparkle activation, including resume; an already queued start either wins the lock and delays admission, or loses and is rejected. Keep the lease through host termination/replacement or a positively verified no-installer abort. Do not release it on a timer, a missing PID, cycle-finished callback or sessionInProgress=false alone. Unknown cancellation enters recovery-required and remains dormant. The native app stops/reaps the service on termination, and the new app resolves the journal before allowing any scan. Hidden windows defer immediate restart to a suitable explicit quit; normal quit may complete an already admitted Sparkle update. Before admission, revalidate the current grant with a generation-bound request; then disabling automatic installation/removing access cancels eligibility. After admission, show Installing, disable conflicting controls and preserve the journal/lease.
8. A one-use update-relaunch marker is written only on the actual updater relaunch path, bound to transaction, target path, old/expected build, boot identity and a short validity window. Consume it atomically before first dashboard startup. Successful update relaunch stays dormant, verifies the expected installed signature/version and native/service readiness, writes an acceptance receipt and only then resolves admission. A subsequent ordinary user launch retains the visible 30-second scan. Stale, malformed, duplicate, wrong-build or crash/pending markers cannot silently authorize normal operation; they produce explicit recovery state where needed. Test marker consumption and manual-open/race behavior. The marker is an operational intent record, not protection against a determined same-user attacker.
9. Retain a verified previous application and manifest before admitting installation. Keep the preserved original installation backup separate from a bounded two-version update-backup rotation; never prune the original as part of that rotation. Ship a separately launchable, Developer-ID-signed/notarized Machine Monitor Recovery.app in the initial private install package, outside the replaceable main app, so a friend can recover when the main app cannot launch. Normal updates still use stock Sparkle; recovery is an explicitly selected, narrow restoration operation. Recovery validates owner-only canonical state/paths, backup hashes, Apple trust/team/bundle identity and sealed data-format compatibility, then acquires the shared operation lock, asks any verified running main app to quit cooperatively, and refuses unknown ownership or a pending installer. Accepted transaction/new-app acknowledgement plus the operation lock can establish the clean restoration case. For an interrupted/unknown installer transaction, require a changed OS boot identity and opening Recovery before the main app; do not infer installer absence from a timer/process list or kill an unknown helper. This provides a concrete safe recovery path after a restart rather than racing Sparkle. Under verified quiescence, stage a checked backup on the target volume, preserve the failed app in a named recovery slot, and atomically rename the staged backup into the exact owner-writable target. Recovery has its own durable phase journal (prepared, target-saved, backup-published, accepted/rolled-back) with canonical target/stage/saved-target identities and verified manifests, persisted and directory-synced before/after each rename. Startup reconciliation resolves each interrupted phase under the shared lock, validating identities/hashes rather than path existence. If the second rename fails, restore the saved target and retain the good backup. A crash after either rename or before receipt persistence preserves good bytes and resumes the exact journaled restoration, without guessing which copy is authoritative. Refuse administrator-owned/nonwritable targets instead of adding a privileged helper. Recovery never auto-reenables update access, starts collection or opens the restored app without an explicit user action. Automatic precommit abort/recovery and explicit postcommit restoration are separate outcomes and tests. A failed first launch retains verified prior bytes and a friend-usable Recovery action; it does not claim automatic restoration while installer ownership is unknown.
10. Access operations carry a monotonically changing in-memory credential generation. Every validation/network/download/preflight completion checks that generation before storing a Keychain item or advancing state. Remove Access cancels owned requests and clears pre-admission staging. Replacement preserves current access until the new grant validates and then commits only if its generation is still current. Remote revocation blocks subsequent protected requests; it cannot revoke bytes already downloaded. Browser reset aborts requests, clears file-input/token references and revokes object URLs; do not claim JavaScript securely erases memory.


## Release and access API

- Public GET / renders a small first-download page without exposing protected release metadata or archives. A recipient selects their access file and clicks Download Machine Monitor (a package containing the main and separate Recovery applications plus short Finder installation instructions); the browser keeps the credential in memory only. No secret query strings, localStorage, analytics or third-party assets.
- Protected POST /v1/access/check validates the selected app-scoped credential and returns only its grant status/expiry and supported app scope.
- Protected GET /v1/apps/{app}/channels/{channel}/manifest returns one qualified release: schema/version, application ID, build/display version, minimum OS, architecture, expected team/bundle ID, immutable archive path/size/SHA256/Ed25519 signature, merged source revision and qualification identifier. Client still validates actual archive/code; fields cannot override compiled identity/trust/origin.
- Protected GET /v1/apps/{app}/releases/{release}/{archive|package}/parts returns the bound piece descriptor; GET/HEAD of its /<index> suffix returns one authorized piece. Every request rechecks entitlement, with Range and conditional requests rejected after authorization. The unsuffixed aggregate locators return unavailable after authorization; there is no aggregate streaming or cache fallback.
- Owner-only tooling uses the owner's Cloudflare session to create/revoke named opaque grants and publish qualified manifests. It creates 256-bit random recipient secrets, stores only hashes in D1 and writes a mode-0600 .machine-monitor-access file for the intended recipient. Tokens are never command-line arguments, source, logs, public CI artifacts or chat. The owner shares recipient files through their chosen private channel; this work sends no messages to friends. The app supports file import/open with strict schema/size/origin/app validation and server validation before Keychain storage. Imported files cannot change the trusted origin or install an app/update by themselves.

# Free-only private update delivery

Scope: this successor records the selected qualification design; acceptance of the record itself creates no resources, billing or binary publication.

The operator selected “Keep hard $0; qualify free alternative” after reviewing R2's potential overages. Retain private downloads for the owner and invited friends, individual revocation, verified automatic updates, local-only telemetry and all prior source/release/installation gates. Billing must never be activated, including R2 subscription checkout, Workers Paid, paid features, trial conversion or a paid/public fallback. This amendment replaces only the previous R2 binary-storage selection, preserving all frozen predecessor records.

## Selected candidate

Use the existing Cloudflare account only after positive, account-bound, timestamped verification of Workers Free. Keep Worker authorization and current-primary D1; store immutable binary parts in Workers Static Assets with assets.run_worker_first=true for ALL requests. No negative patterns, asset-first paths, redirects, SPA/not-found fallback, public part routes, asset custom hostnames or unauthenticated alias may bypass the Worker. Preview/version URLs must be disabled or demonstrably denied. Initial deployment is single-version only, read back as 100% on the reviewed trusted source. No alternate or 0%-traffic version may remain in the active deployment. Cloudflare-Workers-Version-Overrides can select a version in an active deployment at the canonical hostname: explicitly test the override header and every active version, rather than assuming preview-URL suppression covers it. If custom routes are used, their failure mode must be fail-closed; no origin/static fallback is allowed on CPU, quota or runtime failure. Every external request-URL origin is checked against the configured canonical HTTPS origin before routing. Native clients may omit the browser Origin header; an absent header is not an authentication bypass. Unknown or paid subscription state prevents all resource creation, upload, deployment and promotion; an account type, usage-model string or arbitrary local boolean is insufficient evidence. Never downgrade an existing account or create another one silently. Keep account-bound, timestamped plan observations private; source records and OAuth success do not prove the live subscription.

## Storage, privacy and publication

The operator approved smaller authenticated downloads after real whole-file streaming exceeded the accepted 10 ms Workers Free CPU target. This successor replaces server-side concatenation and whole-artifact GET/HEAD transport; all PRD requirements, user-facing design, hard $0, individual grants, scan/install admission, code trust and Recovery requirements remain mandatory. Existing frozen specifications and evidence remain unchanged.

Stage new signed updater and first-install ZIPs as ordered immutable content-addressed pieces of at most 256 KiB. Retain the 512 MiB artifact bound: at most 2048 pieces, with every non-final piece exactly 256 KiB. Preflight the complete retained deployment against 20,000 files; smaller pieces increase request/file counts and do not prove all future fleet sizes fit. Retain all old 20 MiB and 1 MiB assets and immutable publication rows; they need not be restaged or deleted. Their old aggregate endpoints fail unavailable after authorization, rather than continuing an unqualified expensive request or exposing a fallback. Preserve the original application and every installed version in verified recovery copies until candidate qualification and owner acceptance. A CPU-failing candidate cannot become stable merely because source checks or synthetic tests pass. New releases receive new identities; do not mutate qualified archives, signatures, hashes or immutable rows.

The existing signed release manifest and archive/package descriptors remain unchanged. Each descriptor path is now an artifact identity locator: clients GET its `/parts` suffix for a closed `machine-monitor/artifact-parts/v2` descriptor and GET `/parts/<canonical-zero-based-index>` for bytes. No client/server may infer or accept an arbitrary host, URL, asset key, redirect, query, Range, conditional header or unknown field. The descriptor contains exactly schema, app_id, release_id, kind, artifact_sha256, artifact_size, part_size and parts. Each ordered part contains exactly index, size and sha256; paths are derived locally from the already validated artifact locator. Bind app, release, kind, total size and full hash to the signed-release descriptor; validate canonical contiguous indexes, count, complete summed size, piece bounds and lowercase 64-hex SHA256. Require part_size to equal 262144. All counts, indexes, sizes and totals must be non-boolean JSON safe integers: 1..2048 entries, index 0..2047, size 1..262144, artifact_size 1..536870912; an overflow or fractional value is invalid. Bound wire descriptor JSON to 256 KiB and 2048 entries. Reject duplicate keys and incomplete/reordered/unknown/overflowing metadata. Internal D1 metadata retains separately validated immutable content-addressed paths, never returned as a public asset fallback. Bound internal compact parts JSON to 1 MiB before parsing, allowing 2048 rows with maximum-length release IDs; its closed scalar fields, exact paths, totals, canonical representation and legacy-retention distinction remain validated. The artifact wire descriptor is separately bounded to 256 KiB. Canonical piece indexes range from 0 through 2047; reject out-of-range or noncanonical values before any asset read, after authorization.

Every descriptor, piece GET and piece HEAD begins with a fresh current-primary D1 query that itself joins authorization, revocation, expiry and exact app/channel/release entitlement before any private asset is read. A valid owner qualification grant cannot grant stable access implicitly; invited grants cannot read qualification. No authorization cache or eventually consistent permission store is introduced. A revoked or expired grant is denied on the next piece request. Already downloaded bytes cannot be recalled.

Serve one bounded piece per byte request with exact length and EOF validation, cancellation and deadlines. The Worker may buffer at most one 256 KiB piece plus a guard byte before emitting its response; EOF, cancellation and the deadline must be resolved before emitting successful bytes. It does not buffer a multi-piece artifact. Read only that private bound asset through a newly constructed internal request with no bearer/cookie/override forwarding. Do not concatenate, buffer or hash a whole artifact in the Worker. A piece larger than the new bound or malformed internal metadata fails unavailable. A missing, truncated, oversized, stuck, cancelled or quota-failed piece cannot complete a valid assembled update. Keep all protected responses no-store/no-CORS, authenticate before conditional/Range rejection, retain canonical-origin and unconditional worker-first restrictions, disable preview/version aliases, and test override headers across every active deployment version. Each request has bounded subrequests independent of full artifact size.

The native downloader requests pieces sequentially, validates each exact length/hash and writes ordered verified bytes to one newly created owner-only no-follow staging file. An incomplete or cancelled operation removes only its owned partial file. Preserve credential-generation checks across metadata requests, piece transitions, hash/write completion and final completion; cancellation must not allow late callbacks to start another piece or accept an obsolete credential. Use one 300-second overall deadline spanning descriptor, all piece requests, hash/write work and final completion, in addition to per-request deadlines. Never reset that deadline between pieces. Retain full ZIP length/SHA256/Ed25519 verification from a retained file descriptor, code identity checks, safe extraction and stock Sparkle admission. Piece hashes do not replace final publisher verification. No credential or partial ZIP is published to a public path.

The browser keeps one selected credential in memory, requests the descriptor and pieces sequentially with bounded per-request deadlines and one 300-second overall deadline covering descriptor, all pieces, hashes and save-link completion, checks each exact size/hash and full ZIP size/hash, and only then offers the completed Blob for saving. At most the existing bounded whole first-install ZIP is retained locally; no access file, URL token, localStorage, analytics or third-party script is introduced.
